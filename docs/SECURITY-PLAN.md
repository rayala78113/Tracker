# Tracker Security Plan

## Confirmed finding

Supabase security advisors report that row-level security is disabled on:

- `public.tasks`
- `public.task_history`
- `public.task_attachments`
- `public.recurring_tasks`

The current frontend uses a Supabase publishable/anonymous key and accesses `public.tasks` directly. A publishable key is expected in browser code, but it is only safe when database authorization is enforced with suitable RLS policies.

## Immediate rule

Do not enable RLS in production until authentication and matching policies have been implemented and tested. Enabling RLS without policies would stop the existing frontend from reading and updating tasks.

## Required controls

1. Add Supabase authentication.
2. Add a profile or membership model for authorized Tracker users.
3. Add an ownership/team identifier to operational records where required.
4. Enable RLS on every exposed application table.
5. Add separate `SELECT`, `INSERT`, `UPDATE`, and `DELETE` policies.
6. Include both `USING` and `WITH CHECK` for update policies.
7. Keep service-role and OpenAI keys only in Edge Function secrets.
8. Require valid JWTs for AI Edge Functions.
9. Log material task changes to `task_history`.
10. Test policies using authenticated and unauthenticated sessions before production release.

## Initial access model

The first secure version can use a small team model:

- Authorized Tracker members may read operational tasks.
- Authorized members may create and update tasks.
- Destructive delete access should be limited or replaced with soft deletion.
- AI may propose changes but may not apply them without user approval.

A future version can separate administrator, manager, operator, and read-only permissions.

## Delete protection

The present application permanently deletes tasks from the browser. The safer design is:

- Add `deleted_at` and `deleted_by` fields.
- Hide deleted records from ordinary views.
- Preserve their history.
- Restrict permanent deletion to an administrator process.

## Audit requirements

Audit history should capture:

- Task creation
- Title or section edits
- Assignment changes
- Follow-up changes
- Today/tomorrow pinning
- Completion and reopening
- Notes changes where appropriate
- AI-created or AI-proposed content
- Deletion or restoration

## AI security

- Never put an OpenAI API key in `index.html`, Amplify public environment variables, or client-side JavaScript.
- Call OpenAI only from a Supabase Edge Function.
- Validate the authenticated user inside the function.
- Restrict accepted input size.
- Return a structured task draft.
- Do not permit arbitrary database queries generated by the model.
- Use predefined application functions for later AI read/write capabilities.
